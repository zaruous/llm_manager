## 3. 원인 — 세 층

### 3.1 직접 원인: 업데이트 스크립트가 앱 종료 순간 강제 종료된다

**포렌식 근거**
- PowerShell 이벤트 로그: 업데이트용 PowerShell 2건이 Id=400(시작)·Id=800(Add-Type)은 남기고
  **Id=403(엔진 정상 종료)을 남기지 않음**. 같은 시간대 다른 PowerShell 10여 건은 전부 403이 있음 → 강제 종료.
- robocopy가 설치본에 0건 → `powershell`만 아니라 `cmd`까지 죽었다
  (powershell만 죽이는 실험에서는 cmd가 살아남아 부분 해제본을 robocopy로 밀어 넣는다).

**1차 결론(v1.2.2)과 그 한계**
- 유일한 트리 kill 코드였던 ShutdownHook의 `stopAllSync()` → 낡은 PID 파일로 `taskkill /F /T`
  (Windows PID 재사용 실측: 300회 spawn 중 10%)를 원인으로 보고 순서 역전·PID 검증으로 막았다.
- 그러나 v1.2.2로 올리는 업데이트도 **같은 위치**에서 죽었다. 서비스가 하나도 돌지 않아 taskkill 경로는
  실행조차 되지 않았으므로 다른 메커니즘이 있었다.

**진짜 원인: jpackage 런처의 Job Object**
- `LLMManager.exe` 런처는 자기 자신을 자식으로 재실행하고, 그 자식(앱 JVM)을 `KILL_ON_JOB_CLOSE` Job에 넣는다.
  `IsProcessInJob` 실측: **부모 런처 false, 자식(앱) true**.
- 앱이 `cmd /c start`로 분리한 스크립트도 이 Job을 상속한다. 앱 `System.exit` → 런처 종료 → Job 핸들 닫힘 →
  Job 안의 모든 프로세스 강제 종료 = 스크립트가 `:waitapp` 루프 중 로그 3줄만 남기고 사라진 이유.
- 재현(KILL_ON_CLOSE Job 안의 부모가 3초 뒤 종료):

  | 기동 방식 | Job 부모 | Job 없는 부모 |
  |-----------|---------|--------------|
  | `cmd /c start "" /MIN cmd /c bat` (v1.2.2) | **3틱 사망** | 12/12 생존 |
  | WMI `Win32_Process.Create` | **12/12 생존** | 12/12 생존 |
  | 직접 자식 (대조군) | 3틱 사망 | 12/12 생존 |

  스파이크①이 순수 `javaw` 부모로 "생존"을 확인했던 것이 함정이었다 — 실제 런처에는 Job이 있다.

### 3.2 그 아래 깔려 있던 결함 (v1.2.2에서 제거)

| 결함 | 영향 | 수정 |
|------|------|------|
| `timeout /t 5 /nobreak` | 콘솔 없는 프로세스가 띄운 cmd에서 stdin이 파이프 → `Input redirection is not supported`로 즉시 실패, 유예 0초. 리다이렉트로도 못 살림(errorlevel 125) | 앱 PID 소멸 폴링(`tasklist`/`findstr`) + 2초 유예 |
| `start /B` + JVM 파이프 상속 | 부모 JVM 종료 후 자식이 stdout에 쓰는 순간 즉사(재현) | stdin NUL, stdout/stderr DISCARD; 스크립트는 자기 로그 파일에만 기록 |
| errorlevel 미검사 | Expand-Archive가 중간에 끊겨도 robocopy 강행 → 부분 해제본이 설치본을 덮어씀(실험: 53개 부분 파일 복사) | Java에서 해제 + zip 엔트리 수 검증(Zip Slip 가드), robocopy exit≥8 실패 판정, 실패 시 재기동 안 함 |
| 고아 PID `taskkill /F /T` 무검증 | 재배정된 PID면 무관한 프로그램을 죽임 | `PidFileManager.check()` — PID 파일 2행 `start=<epochMillis>`(구버전은 mtime)과 실제 시작 시각 대조, `LIVE_MATCH`만 kill |
| `stopAllSync` 이중 호출 | `AppContext.shutdown()`과 ShutdownHook이 연달아 taskkill | `stopAllDone` 가드, 죽은 `process`는 skip |
| `%~dp0` 폴백 | 후행 백슬래시가 `"C:\dir\"`로 따옴표를 깨뜨림 | 폴백 제거 — 설치 경로 미확인 시 진행 안 함 |
| 도구 이름만으로 호출 | Git for Windows `usr\bin`이 PATH 앞이면 `find`가 GNU find → 대기 루프 0초 종료(E2E에서 발견) | `%SystemRoot%\System32\*.exe` 절대 경로 |

## 7. 남은 제약 · 운영 메모

- **첫 홉**: 업데이트를 수행하는 것은 실행 중인 옛 버전의 코드다. v1.2.2 이하 설치본은 다음 업데이트가
  (안전하게) 실패하므로 인스톨러로 한 번 갈아타야 한다.
- 설치 위치가 Program Files면 robocopy가 ACCESS DENIED → 인스톨러는 `--win-per-user-install`(`%LOCALAPPDATA%`).
- robocopy `/E`는 대상에만 있는 파일을 지우지 않는다. `/PURGE`·`/MIR`은 `app/service-packs/*.yml` 사용자
  데이터를 지우므로 금지 → `app/lib`에 구 버전 jar가 남는다(cfg는 새 jar를 가리키므로 무해).
- WMI를 쓸 수 없는 환경은 `start` 폴백 — 이 경우 Job에 죽을 수 있다(그래도 안전 실패).
- CI 산출 zip은 `lib/*.jar` 번들(gitignore)을 포함하지 않는다. 로컬 번들 jar는 robocopy 후에도 남는다.
- `build/installer/LLMManager`는 gradle 산출물이라 `jpackageImage`가 통째로 지운다 — 정식 설치 위치로 쓰지 말 것.
- 스크립트 로그: `%TEMP%\llm-manager-update\update.log`. 실패 알림에 경로가 포함된다.

## 8. 배운 점

- **재현은 실제 런처 조건으로.** 순수 `javaw` 부모로는 통과했지만 jpackage 런처에는 Job이 있었다.
  `IsProcessInJob`으로 먼저 확인했다면 하루를 아꼈다.
- Windows에서 "부모 프로세스 트리 밖"과 "Job Object 밖"은 다르다. `taskkill /T`는 살아있는 부모-자식 체인만
  따라가지만, Job은 상속된다. Job을 벗어나려면 WMI/Task Scheduler처럼 **다른 프로세스가 생성**해야 한다.
- `timeout`, `find`, `Start-Process -Wait`(자손까지 대기) 같은 셸 도구의 전제조건을 의심할 것.
- Gradle `processResources { expand(...) }`의 클로저 값은 입력으로 추적되지 않는다 — `inputs.property` 필수.
- 방금 컴파일한 미서명 P/Invoke exe는 Defender가 실행 전에 격리할 수 있다 → PowerShell `Add-Type` 인메모리로 대체.
